今回何を作ったのかと言うと
階層式のデバッグメニューですね【実演】
3回タップで出ます
こんな感じで階層メニューになってます
動的にUIを追加できます
エディタウィンドウ版もあります

軽く使い方について説明すると
DebugPageを継承したクラスを作る
で、それのConfigureメソッドをoverrideする

ここまでで既に見せましたが、いくつかこだわりポイントがあって

その1 BuilderAPI
Configureの引数で渡されるIDebugUIBuilderってのが、前提VisualElementなら概ね何でも追加できるようになっていて
このLabelとかIntegerFieldとかも全て拡張メソッドになってます
ので、ユーザーの拡張性は高いです
Foldoutに渡してるラムダの中身が、引数がIDebugUIBuilderになってるのがちょっと面白ポイントです

その2 UIの動的追加
Configure時じゃなくても、ページインスタンスを取得したうえで、AddDebugUIなどのメソッドで後からUIを追加できます
このとき返るIDieposableをDisposeすると、削除されます
例えば特定の敵のHPを操作するデバッグコマンドを追加して、AddToで敵の寿命に紐づけるとか

その3 EditorWindow
あらためて。【実演】
ランタイム側と同じデバッグメニューを、エディタウィンドウとして表示できます
これは内部実装的には、本当に同一インスタンスで。ランタイム側から引っこ抜いてエディタウィンドウにぶっ挿してるような感じになってます

で。そもそも、なぜ自作したのか、なんですけど
似たようなことができる既存の選択肢というのはあります。ただ、いくつか不満がありました

SRDebuggerは、階層メニューが作れないので、デバッグコマンドまみれになって視認性が悪くなりがちという問題があります
UnityDebugSheetは、その点かなりいいです。ぶっちゃけこれでいい。ただ不満はいくつかあって。ボタンのデザインが致命的にボタンっぽく見えなさすぎるとか、拡張はできるけどちょっと面倒な手続きが多いとか。

その辺、本パッケージはUIToolkitを使用しているので、拡張するにあたってプレハブを登録しとく必要とかないし、見た目変えたいだけならそもそもC#いじらなくていい

そういうわけで、本パッケージではUIToolkitを使ってるので、そこについても掘り下げておきます
UIToolkit、正直なところ一長一短が激しくて。

良いところは、今の時代としては何と言っても、AIエージェントとの相性の良さですね。
UGUIと比べれば、圧倒的にこちらの方が高い精度でレイアウトを組んでくれます。uxmlは結局ただのテキストファイルですからね。レビューしやすい。

効率もすごくいい。UniCLIとか使ってゴリ押しでUGUI作るときよりもはるかにトークン消費少なく済みます

ただ正直なところ今回のパッケージを通して、罠もだいぶ多かったです。
結果から述べると、エンタープライズでの開発において、ランタイムUIに使うのは保守が無理かなと

まず「PointerDownイベントが届かない」。これはカスタムテーマを実装するときに詰まったとこです
ボタンを押している間だけ色を変えて、離したら元に戻そうとしたところ、PointerDownイベントを取ることができなくて。これ何故かというと、内部実装的には、わざとイベントを止めて外に流さない実装になっているという。けどButtonはVisualElementには違いないので、普通にコールバックは取れそうなコードがコンパイルを通ります。罠すぎる。
結果として、Clickable を継承して ProcessDownEvent / ProcessUpEvent にフックを差し込む形になりました。

次に「PointerUpイベントが取れない」。これは ScrollView のスクロールバーをカスタムしたときに詰まったとこです
デバッグメニューは項目が多くなるので、縦スクロールバーの dragger もちゃんと hover / pressed の色を揃えたいんですよね
押したときに色を変えるところまではいけるんですが、指を離したタイミングの PointerUp が取れなくて、素直に書くと押されっぱなしの見た目が残ります
これ何故かというと、Slider の内部実装がドラッグ中のイベントをかなり握っていて、外側から期待通りに PointerUp を拾えないという
なので最終的には PointerUp ではなく、PointerCaptureOut を「ドラッグ終了」として扱う実装にしました
これも、やりたいことはただ色を戻したいだけなのに、見るイベントが急に低レイヤーになる。罠すぎる

最後に「USSだけで完結しない」。これもカスタムテーマでだいぶ困りました
最初は CSS みたいに、USS の hover や active に背景色を書けば終わりだと思っていました
ただ実際には、Unity のデフォルトテーマ側が背景色を上書きしてきたり、Button の PointerDown が取れなかったりして、USS だけでは押下中の見た目を安定して制御できませんでした
なので色の定義は USS に置きつつ、押した、離した、hover した、みたいな状態遷移は C# 側で inline style を入れる形にしました
見た目は USS、状態管理は C#。この分担自体は悪くないんですが、最初に期待していた「見た目だけなら USS で完結する」とはズレていて、ここもかなりハマりました

最適化について
display:noneを使うと、レイアウト計算が飛ばされるので、初回表示時にスパイクすることがあります
なので、画面外の滅茶苦茶遠くへtranslateしておくという方法を取ることで、レイアウト計算をゲーム開始タイミングに寄せることができ、フレーム落ちを確実に回避できるようになりました
なんと、Unity公式のリファレンスに乗ってる手法です

まとめ
UIToolkitはAIエージェントとの相性については本当に良い
ただ、罠が多すぎる。基本的に驚き最小の原則の逆張りをしていて、内部実装との格闘が多すぎて、これは厳しい。
個人開発で、UIToolkitのトラブルは全てAIエージェント+上位モデルにお任せする、とかならアリなのかもしれない。
